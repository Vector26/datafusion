Side path: listing tables & partition pruning

You landed in catalog-listing/src/helpers.rs because that file implements “can we skip reading whole folders of Parquet?” It only runs when (1) data was registered as a listing table, (2) the query has filters on partition columns, and (3) the optimizer pushed those filters down far enough.

The line you saw (in plain language)
is_applicable &= col_names.contains(&name.as_str());

// Meaning: "This pruning expression references column `name`.
// If `name` is NOT one of the table's partition columns, the whole
// rule is marked not applicable — don't use it to skip folders."
// Why: otherwise a filter on a normal data column could be mistaken
// for a partition key and you'd skip data incorrectly (wrong results).

What DataFusion is (60 seconds)

DataFusion is an embeddable query engine written in Rust. You embed it in a binary (or use the CLI) like you’d embed SQLite — but oriented toward analytical SQL over columnar data (Parquet, Arrow), not OLTP row storage. It is not a single running “database server” unless you build one on top.

Two loops you care about

  1. Outer loop (your learning): get dummy data → register → query → see results → EXPLAIN → pick one stage to read in source.
  2. Inner loop (every query): parse SQL → logical plan → analyze → optimize → physical plan → execute in parallel → stream Arrow batches.

Why the first DAG felt useless

Mixing both loops into one small canvas put 15 steps on 11 vertical layers with labels inside tiny circles — that was a layout failure, not the idea. This version separates views and gives each step a full paragraph when selected.

Concrete first afternoon (suggested, not mandatory)

  • Build or download one Parquet file (even small).
  • Run datafusion-cli or a datafusion-examples dataframe example.
  • CREATE EXTERNAL TABLE ... LOCATION '...' or register API equivalent.
  • SELECT count(*) ... then EXPLAIN / EXPLAIN ANALYZE.
  • Only then open catalog-listing if your table is directory-partitioned.
